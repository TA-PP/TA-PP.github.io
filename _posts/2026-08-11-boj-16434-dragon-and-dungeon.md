## 문제 정의

[백준 16434번 드래곤 앤 던전](https://www.acmicpc.net/problem/16434)은 용사가 1번 방부터 `N`번 방까지 순서대로 이동하면서 모든 몬스터를 쓰러뜨리기 위해 필요한 최소 최대 생명력 `HMaxHP`를 구하는 문제다.

방은 두 종류다.

- `t = 1`: 공격력 `a`, 생명력 `h`인 몬스터와 전투한다.
- `t = 2`: 용사의 공격력이 `a`만큼 증가하고 현재 생명력이 `h`만큼 회복된다.

몬스터 방에서는 용사가 먼저 공격하고, 몬스터가 살아 있다면 몬스터가 반격한다. 포션으로 회복해도 현재 생명력은 최대 생명력을 넘을 수 없다.

예를 들어 용사의 공격력이 3이고 공격력 2, 생명력 7인 몬스터와 싸운다고 하자.

```text
용사 공격 1회: 몬스터 HP 7 -> 4, 몬스터 반격
용사 공격 2회: 몬스터 HP 4 -> 1, 몬스터 반격
용사 공격 3회: 몬스터 HP 1 -> -2, 전투 종료
```

용사는 3번 공격하지만 몬스터에게는 2번만 공격받는다. 받은 피해는 `2 × 2 = 4`이므로 이 방을 생존하기 위한 최소 현재 생명력은 5다.

## 접근 및 설계

최대 생명력 후보를 `hmax`라고 정한 뒤, 해당 체력으로 던전을 끝까지 통과할 수 있는지 시뮬레이션했다.

최대 생명력이 커질수록 던전을 통과하기 쉬워진다.

```text
최대 생명력:      작음 ----------------------------> 큼
던전 통과 가능:    불가능 불가능 불가능 | 가능 가능 가능
                                      ↑
                              찾아야 할 최소 가능 값
```

통과 가능 여부가 한 방향으로만 바뀌므로 이분 탐색으로 최소 최대 생명력을 찾을 수 있다. 처음 코드부터 최종 형태까지 수정한 과정을 단계별로 복기했다.

### 1단계: 입력 데이터와 공격력을 직접 변경

```python
while dungeon[room][2] > 0:
    dungeon[room][2] -= atk
    hcurr -= dungeon[room][1]

atk += dungeon[room][1]
```

첫 코드에서는 몬스터의 생명력이 저장된 `dungeon`과 용사의 초기 공격력 `atk`를 직접 수정했다.

이분 탐색은 서로 다른 `hmax`를 사용해 같은 던전을 여러 번 검사한다. 첫 번째 검사에서 몬스터 생명력이나 공격력을 변경하면 다음 검사부터는 원래 조건이 아닌 변형된 던전을 탐색하게 된다.

또한 용사가 몬스터를 쓰러뜨린 마지막 공격 뒤에도 무조건 피해를 받아 전투 순서가 잘못됐고, 포션 회복량도 최대 생명력으로 제한하지 않았다.

### 2단계: 매 탐색마다 독립된 전투 상태 사용

```python
tmp_atk = atk
enemy = dungeon[room][2]

while enemy > 0:
    enemy -= tmp_atk
    hcurr -= dungeon[room][1]
```

두 번째 코드에서는 `tmp_atk`과 `enemy`를 만들어 원본 입력이 바뀌지 않도록 수정했다. 이제 각 이분 탐색이 동일한 던전 상태에서 시작한다.

하지만 몬스터를 죽인 직후에도 `hcurr`을 감소시키므로 여전히 반격 횟수가 한 번 많다. 확인을 위해 넣은 `print(hcurr)`도 제출 전 제거해야 한다.

### 3단계: 마지막 공격의 반격 제거와 회복 상한 적용

```python
enemy -= tmp_atk
if enemy > 0:
    hcurr -= dungeon[room][1]
```

몬스터 생명력이 0보다 클 때만 용사가 피해를 받도록 수정했다. 용사가 먼저 공격하므로 몬스터를 쓰러뜨린 턴에는 반격이 없다.

포션 방에서도 현재 생명력이 최대 생명력을 넘지 않게 보정했다.

```python
hcurr += dungeon[room][2]
if hcurr > hmax:
    hcurr = hmax
```

이는 다음처럼 더 간결하게 표현할 수 있다.

```python
hcurr = min(hmax, hcurr + heal)
```

### 4단계: 유효한 하한과 사망 시 중단

```python
left = 1

for room in range(len(dungeon)):
    if hcurr <= 0:
        break
```

최대 생명력은 양의 정수이므로 `left`를 0이 아닌 1로 변경했다. 용사가 이미 사망했다면 남은 방을 확인할 필요가 없으므로 시뮬레이션도 중단했다.

다만 이 검사는 각 방에 들어가기 전에만 실행된다. 한 몬스터와 싸우는 `while enemy > 0` 안에서는 용사가 사망한 뒤에도 몬스터가 죽을 때까지 반복할 수 있어 성능 문제는 남아 있다.

### 5단계: 최대 생명력 탐색 범위 확대

```python
right = 10**18
```

기존의 `right = 1_000_000`은 최소 최대 생명력이 100만을 넘는 입력을 포함하지 못한다. 방 수와 몬스터 능력치가 모두 크면 필요한 체력은 매우 커질 수 있으므로 충분히 안전한 `10^18`을 상한으로 사용했다.

이 단계에서 전투 규칙과 이분 탐색 방향은 올바르게 정리됐다. 마지막으로 몬스터를 한 대씩 공격하는 반복문을 수식으로 바꿔 시간복잡도를 개선했다.

### 최종 개선: 전투를 반복하지 않고 피해량 계산

몬스터 생명력이 `monster_hp`, 현재 용사 공격력이 `current_atk`라면 몬스터를 쓰러뜨리는 데 필요한 공격 횟수는 다음과 같다.

```python
hero_hits = (monster_hp + current_atk - 1) // current_atk
```

이는 정수 연산으로 올림 나눗셈을 구현한 것이다. 몬스터는 마지막 공격 전에 쓰러지므로 반격 횟수는 `hero_hits - 1`이다.

```python
damage = (hero_hits - 1) * monster_atk
current_hp -= damage
```

이제 몬스터 생명력만큼 반복하지 않고 방 하나를 `O(1)`에 처리할 수 있다.

## 사용한 자료구조

### 리스트(List)

각 방의 정보 `[t, a, h]`를 이차원 리스트 `dungeon`에 저장했다.

```python
dungeon = [list(map(int, input().split())) for _ in range(N)]
```

- 몬스터 방: `[1, monster_atk, monster_hp]`
- 포션 방: `[2, attack_increase, heal]`

이분 탐색에서 최대 생명력 후보가 바뀔 때마다 같은 던전을 처음부터 다시 통과해야 하므로 모든 방 정보를 저장한다.

중요한 점은 이 리스트를 시뮬레이션 중에 수정하지 않는 것이다. 몬스터 생명력처럼 전투 중 변하는 값이 필요하다면 지역 변수를 사용해야 각 탐색이 서로 영향을 주지 않는다.

## 사용한 알고리즘

### 이분 탐색(Binary Search)

정답이 될 수 있는 최대 생명력 범위 `[1, 10^18]`을 절반씩 줄인다.

- `hmax`로 던전 통과 가능: 더 작은 최대 생명력을 찾기 위해 `right = hmax - 1`
- `hmax`로 던전 통과 불가능: 더 큰 최대 생명력이 필요하므로 `left = hmax + 1`

반복 종료 후 `left`가 던전을 통과할 수 있는 최소 최대 생명력이다.

### 매개변수 탐색(Parametric Search)

최솟값 문제를 다음 결정 문제로 바꾸었다.

> 최대 생명력이 `hmax`일 때 용사가 던전의 마지막 방까지 생존할 수 있는가?

`hmax`가 증가하면 통과할 수 없던 던전을 통과할 수 있게 되지만, 통과할 수 있던 던전이 다시 불가능해지지는 않는다. 이 단조성이 이분 탐색의 근거다.

### 전투 시뮬레이션과 올림 나눗셈

각 최대 생명력 후보마다 공격력과 현재 생명력을 초기화하고 방을 순서대로 처리한다.

몬스터 방의 피해량은 다음 공식으로 한 번에 계산한다.

```text
용사의 공격 횟수 = ceil(몬스터 HP / 용사 ATK)
몬스터 반격 횟수 = 용사의 공격 횟수 - 1
받는 피해 = 몬스터 반격 횟수 × 몬스터 ATK
```

포션 방에서는 공격력을 증가시키고 현재 생명력을 최대 생명력 이하로 회복한다.

## 시간복잡도

최대 생명력의 탐색 상한을 `H`, 방의 개수를 `N`이라고 하자.

- 던전 통과 가능 여부 확인: 방을 한 번 순회하므로 `O(N)`
- 최대 생명력 이분 탐색: `O(log H)`
- 전체 시간복잡도: **`O(N log H)`**
- 공간복잡도: 방 정보를 저장하므로 **`O(N)`**

여기서 `H = 10^18`이면 이분 탐색은 약 60번 수행된다.

몬스터를 한 대씩 공격하는 기존 코드는 한 방의 처리 시간이 몬스터 생명력과 용사 공격력에 따라 달라진다. 이를 피해량 공식으로 바꾸어 방마다 `O(1)`에 처리해야 전체 시간복잡도를 보장할 수 있다.

참고로 이 문제는 누적 피해량을 관리해 `O(N)`에 직접 최소 체력을 계산하는 풀이도 가능하다. 이번 글에서는 실제로 사용한 최대 생명력 이분 탐색 과정을 중심으로 정리했다.

## 알고리즘 흐름(텍스트 다이어그램)

```text
[N개의 방 정보 입력]
          |
          v
[최대 생명력 범위: left = 1, right = 10^18]
          |
          v
[hmax = (left + right) // 2]
          |
          v
[현재 HP = hmax, 현재 ATK = 초기 공격력]
          |
          v
[1번 방부터 순서대로 시뮬레이션]
       /                     \
 [몬스터 방]               [포션 방]
       |                       |
       v                       v
[반격 횟수 계산]       [ATK 증가, HP 회복]
[HP에서 피해 차감]     [HP는 hmax 이하]
       \                     /
        v                   v
        현재 HP <= 0 인가?
          /            \
        Yes            No
         |              |
         v              v
   [통과 불가능]    [다음 방 또는 통과]
         |              |
         v              v
 left = hmax + 1   right = hmax - 1
          \            /
           v          v
      [left <= right 동안 반복]
                 |
                 v
 [left = 통과 가능한 최소 최대 생명력]
```

## 최종 제출 코드

```python
import sys

input = sys.stdin.readline

N, initial_atk = map(int, input().split())
dungeon = [list(map(int, input().split())) for _ in range(N)]


def can_clear(max_hp):
    current_hp = max_hp
    current_atk = initial_atk

    for room_type, attack, hp in dungeon:
        if room_type == 1:
            hero_hits = (hp + current_atk - 1) // current_atk
            monster_hits = hero_hits - 1
            current_hp -= monster_hits * attack

            if current_hp <= 0:
                return False
        else:
            current_atk += attack
            current_hp = min(max_hp, current_hp + hp)

    return True


left = 1
right = 10**18

while left <= right:
    mid = (left + right) // 2

    if can_clear(mid):
        right = mid - 1
    else:
        left = mid + 1

print(left)
```

로컬 테스트를 위해 사용한 아래 코드는 백준 제출 시 제거해야 한다.

```python
sys.stdin = open('./input/dragon_and_dungeon_input.txt', 'r')
```

디버깅을 위해 반복문 안에 작성한 `print(hcurr)`도 제출 전에 반드시 제거해야 한다.

## 오늘의 회고(실수한 점 포함)

이번 문제는 최대 생명력을 답의 후보로 두고 던전 통과 여부를 검사한다는 큰 방향은 처음부터 잘 잡았다. 체력이 커질수록 통과 가능성이 높아지는 단조성을 이용한 이분 탐색이었다.

하지만 시뮬레이션 문제에서는 작은 상태 관리 실수가 다음 이분 탐색까지 오염시킬 수 있다는 점을 놓쳤다.

1. **원본 던전과 초기 공격력을 직접 변경했다.**

   이분 탐색의 각 검사는 동일한 초기 조건에서 시작해야 한다. `enemy`, `current_atk` 같은 지역 변수를 만들어야 한다.

2. **몬스터가 죽은 마지막 턴에도 피해를 받았다.**

   용사가 먼저 공격하므로 몬스터가 쓰러졌다면 반격은 없다. 공격 횟수보다 몬스터 반격 횟수가 정확히 1 적다.

3. **포션 회복 후 최대 생명력을 넘겼다.**

   현재 생명력은 `min(max_hp, current_hp + heal)`로 제한해야 한다.

4. **탐색 상한을 100만으로 잡았다.**

   이 문제의 정답은 100만보다 훨씬 클 수 있다. 입력 제한으로 가능한 최악의 상황을 생각하고 충분한 상한을 설정해야 한다.

5. **몬스터를 실제 공격 횟수만큼 반복했다.**

   전투 규칙은 맞더라도 입력이 크면 시간 초과가 발생할 수 있다. 반복되는 전투를 올림 나눗셈으로 바꾸면 공격 횟수와 피해량을 즉시 계산할 수 있다.

특히 시뮬레이션을 이분 탐색의 결정 함수로 사용할 때는 결정 함수가 최대 약 60번 반복된다는 점을 기억해야 한다. 한 번의 시뮬레이션 안에 큰 `while` 반복이 있으면 전체 실행 시간이 급격히 증가한다.

앞으로는 다음 순서로 확인해야겠다.

```text
원본 입력을 수정하고 있지 않은가?
-> 매 탐색마다 상태가 완전히 초기화되는가?
-> 문제의 행동 순서를 정확히 반영했는가?
-> 반복 계산을 수식으로 바꿀 수 있는가?
-> 정답의 최악 범위를 상한에 포함했는가?
```

이번 문제를 통해 이분 탐색의 범위와 조건뿐 아니라, 그 안에서 실행되는 시뮬레이션의 정확성과 시간복잡도까지 함께 설계해야 한다는 점을 복기했다.
